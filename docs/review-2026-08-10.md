# Cross-check of the hardening and Nautilus review, 2026-08-10

Recorded: 2026-08-10. Reviewed tree: `e0d016d`.

## Context

This document cross-checks
[`marcel_hardening_review_and_nautilus_lessons.md`](../marcel_hardening_review_and_nautilus_lessons.md)
(Review C) against the source it describes, and turns the surviving findings
into a delivery plan. Review C is a synthesis of
[`review-2026-08-05.md`](review-2026-08-05.md), the repository's own validation
notes, and a second source-level inspection. Like Review B before it, it could
not clone or build the repository.

Every claim below was checked by reading the exact code path. Findings carry an
explicit verdict and a re-tiering where Review C's severity does not match
reachability.

Review C reports the repository's 181-test claim as unverified repository
evidence, because its environment could not build. That claim is now
independently confirmed: `nix develop --command cargo test --all-targets` on
`e0d016d` gives `181 passed; 0 failed` for the library target plus `1 passed`
for the binary target. (The suite requires the Nix dev shell; a plain shell

## Verdict

Review C is accurate. Fifteen of its sixteen P1/P2 findings reproduce in the
source exactly as described; one is wrong in a way that matters. Its central
architectural claim — that `CommittedOperation` solved the single-commit
boundary and left the multi-commit boundary open — is correct and is the right
thing to fix next.

Two calibration problems are worth naming before the plan:

1. **The P1 tier mixes three different kinds of defect.** P1.3 poisons Undo
   history deterministically. P1.4 is a same-uid TOCTOU. P1.8 is an
   architectural gap with no live failure. Treating them as one "release
   blocker" tier makes the fix order harder to reason about than it needs to be.
2. **Browser-projection impact is overstated throughout.** Marcel watches the
   current directory non-recursively with a 250 ms idle / 1 s maximum coalescing
   window (`src/app.rs:912`, `src/directory_watcher.rs:19`). The projection
   desyncs in P1.1 and P1.5 self-correct within about a second. The durable
   damage in both is to Undo semantics, not to what the user sees.

## Confirmed, deterministic

### D1. Compensation reinserts a history record it has already invalidated

*Review C P1.3. Verdict: confirmed. This is the strongest finding in the review
and belongs first, above P1.1.*

`rollback_undone_moves` (`src/file_ops.rs:898`) returns `Result<()>`. When
`undo_operation`'s `Move` arm fails partway (`src/file_ops.rs:589`), it rolls
the already-undone transfers forward and returns an ordinary `Err`
(`src/file_ops.rs:596-601`). `start_undo` reads that `Err` and reinserts the
**pre-attempt** record through `cancel_undo` (`src/app.rs:1812`).

The repository's own review already established the fact that makes this fatal:
*a same-filesystem rename bumps the renamed root's `ctime`*
([`review-2026-08-05.md`](review-2026-08-05.md), "What the fixes changed"). The
rolled-forward roots have been renamed twice, so their `ctime` no longer matches
`expected_state`, and `validate_snapshot_tree` compares the full `FileIdentity`
including `ctime` (`src/file_ops.rs:1794-1804`).

Consequence: after any rollback, every later Undo of that record fails with
*"Cannot continue: … changed or was replaced"* — Marcel blaming an external
actor for its own compensation. The record is permanently poisoned and the
message is actively misleading.

The same shape exists in `rollback_restored` (`src/trash_ops.rs:530`), which
leaves `payload_identity` stale for the same reason.

Review C's placement of this at P1.3 undersells it. Nothing else in the review
is both deterministic and permanently damaging.

### D2. A partial Move record drives both reconciliation and the Undo message

*Review C P1.1. Verdict: confirmed, with a corrected impact statement.*

`start_transfer` derives `DirectoryChanges` from the operation record whenever
one exists (`src/app.rs:2349-2359`). A transfer of two directories where one
contains a Unix socket produces two entries in `completed` and one in
`OperationRecord::Move`, so the socket-bearing directory is omitted from
reconciliation.

Both halves confirmed. But the projection half is transient — the watcher
corrects it. The durable half is the one Review C mentions only in passing:

- A `Move` record covering a **subset** is committed to the journal, so Undo
  silently moves back only some of what the user moved.
- `undo_note` is binary (`src/app.rs:6979-6985`). With `undo_unavailable` set,
  the success notification says *"· not available to Undo"* while a partial
  record sits in the journal and Undo is in fact partially available.

The fix Review C recommends — derive effects from `CompletedTransfer`, treat the
record as metadata only — is right. The policy question it raises (all-or-nothing
versus supported partial Undo) needs deciding, not deferring; see Stage 2.

### D3. Retrash strands committed Trash placements

*Review C P1.7, first sub-claim. Verdict: confirmed, deterministic once record
identification fails.*

`retrash_records` (`src/trash_ops.rs:432-450`) requires every original to
produce an identifiable record. When an item reaches Trash but its entry cannot
be identified, `trash_paths` reports it in `failures` and omits it from
`records` (`src/trash_ops.rs:312-319`). `retrash_records` then compensates only
`outcome.records` and returns `Err`.

The unidentified item stays in Trash. `start_undo`/`start_redo` take the error
branch, reinsert the record, notify failure, and never reconcile — so the
browser keeps listing a file that is now in the Trash.

## Confirmed, but a race rather than a determinism

These need a concurrent same-uid actor. They are real and cheap to close; they
are not the same tier as D1–D3.

### R1. Undo deletion of copy and archive output is not failure-atomic

*Review C P1.6. Verdict: confirmed. Re-tier: the window is narrower than stated.*

`remove_snapshotted_tree` (`src/file_ops.rs:1808-1818`) validates then removes
leaf-first with `?`. A mid-loop failure leaves the tree partly destroyed and
returns an ordinary `Err`, after which `cancel_undo` restores a record claiming
the output is intact.

Discount: `validate_snapshot_tree` runs immediately before and rejects any
added, removed, or changed entry. The only reachable partial-loss window is a
concurrent mutation landing between validation and the failing removal. Review C
presents this as if validation and deletion were far apart.

The existing regression
`copy_undo_refuses_added_children_without_partially_removing_output`
(`src/file_ops.rs:2307`) already pins the non-racing case: a child added *before*
the undo makes validation refuse, and nothing is removed. What is untested — and
what R1 actually is — is a child appearing *after* validation returns. Reusing
`delete_ops`' quarantine-first model closes the residual window; the surrounding
behaviour is already correct.

`delete_ops.rs` already models the correct answer — quarantine each validated
top-level output atomically, then erase — and Review C is right to point there.

### R2. Post-commit identity refresh can adopt a replacement object

*Review C P1.4. Verdict: confirmed as written. Re-tier to P2 by exploitability,
but fix it anyway — it is roughly ten lines.*

`refresh_snapshot_identities` (`src/file_ops.rs:1766-1775`) overwrites the
stored identity from a fresh `symlink_metadata` with no comparison against the
pre-commit snapshot. The same unguarded post-commit stat appears in
`rename_entry` (`src/file_ops.rs:525-531`) and `reverse_rename`
(`src/file_ops.rs:868-874`). `create_directory_at` at least checks `is_dir()`
(`src/file_ops.rs:1868-1874`).

The pre-commit identity is already in hand at every one of these sites, so
refusing to adopt a `(device, inode, kind)` mismatch — and downgrading to
success-without-undo — costs almost nothing.

### R3. Purge re-opens a replacement window it had just closed

*Review C P1.7, third sub-claim. Verdict: confirmed.*

`purge_trash_records` validates `payload_identity` for every record
(`src/trash_ops.rs:92-101`), then hands bare paths to `delete_trash_backings`,
which re-stats and captures its own expected identity
(`src/delete_ops.rs:118-135`). A payload replaced between the two stats is
permanently erased.

### R4. Copy Redo can mark the source removed

*Review C P1.5. Verdict: confirmed. Re-tier to P2: narrow, and watcher-corrected.*

`redone_transfer` (`src/file_ops.rs:749-755`) unconditionally puts
`completed_sources()` in `removed`. It is called from both the Copy
(`src/file_ops.rs:674`) and Move (`src/file_ops.rs:697`) redo arms.

Worth noting as an internal inconsistency: `start_transfer` already guards the
identical fallback on `mode` (`src/app.rs:2351`). One of the two call sites got
it right.

### R5. Trash-root protection is lexical

*Review C P1.9. Verdict: confirmed. Re-tier to P2.*

`paths_overlap_trash_root` (`src/trash_ops.rs:555`) is a pure `starts_with`
pair, and `delete_paths_with_policy` applies it to the lexical path before
quarantine (`src/delete_ops.rs:101`). A regular file reached through a symlinked
ancestor physically inside a Trash root passes the guard; the kernel then
resolves the link during the quarantine rename and the delete.

Reachability requires the user to have created an alias into their own Trash and
to address a child through it. The loss is one trashed file plus an orphaned
`.trashinfo`. Real, but not the tier D1 occupies.

## Confirmed architectural gaps

### A1. Filesystem operations, the journal, and the busy lock are all window-owned

*Review C P1.8. Verdict: confirmed, and incomplete — see M1 below.*

`OperationController` (`src/operations.rs`) has no `Drop`. It holds the
cancellation flag and the GPUI `Task`s, but the work runs inside
`smol::unblock`, which continues on the blocking pool after the entity is
dropped. Closing a window therefore removes the only progress surface and
reconciler while the mutation runs to completion.

Reachability caveat Review C does not state: Marcel has no user-facing New
Window action. Additional windows appear only through
`open_desktop_locations` when a D-Bus request carries more than one location
(`src/main.rs:155-190`). That affects priority, not validity.

### A2. Compound operations have no partial state

*Review C P1.2. Verdict: confirmed as a design gap, but not actionable as
written.*

As stated this is an umbrella over D1, D3, and R1 rather than a finding of its
own — it has no reproduction and no closure criterion. Split it into the four
sites that genuinely cross more than one commit: `undo_operation`'s `Move` arm,
`remove_snapshotted_tree`, `restore_trash_records`, and `retrash_records`.
Everything else in the operation layer commits exactly once, and
`CommittedOperation` already models those correctly.

## Where Review C is wrong

### W1. The permanent-delete completion test is not a defect

*Review C P2, "Permanent-delete completion still conflates stat errors with
absence." Verdict: rejected. The recommended fix would introduce a regression.*

The line in question is:

```rust
if !root_failed && fs::symlink_metadata(&root.quarantine).is_err() {
    completed.push(root.original);
```

Review C reads the `symlink_metadata` error as the proof of deletion. It is not.
Reaching that expression requires `root_failed == false`, which means every
entry in the plan was identity-validated and removed with `Ok` — including
`entries[0]`. `collect_delete_plan` builds the plan pre-order from the
quarantine root (`src/delete_ops.rs:284-321`) and the removal loop runs `.rev()`
(`src/delete_ops.rs:201`), so `entries[0]` is the quarantine root and it is
removed **last**, by `fs::remove_dir`, returning `Ok`. Completion is already
proven. The stat is a redundant confirmation.

Adopting the recommendation — *"other errors must produce an incomplete-delete
failure"* — would make a genuinely complete deletion report as incomplete
whenever a concurrent permission change on the parent makes the confirmation
stat return `EACCES`. That is a false failure introduced into the one module
both prior reviews called the strongest in the codebase.

If anything changes here, it should be to drop the redundant stat, or to match
`NotFound` explicitly and treat other errors as *complete, confirmation
unavailable*.

## Missing from Review C

### M1. The undo journal and the busy lock are per-window, not just the jobs

Review C's P1.8 covers in-flight *jobs*. It does not cover the fact that
`OperationController` also owns `OperationJournal` and the `busy` flag, so with
two windows open:

- Each window keeps an independent undo/redo stack. Window B can mutate a path
  that window A's record depends on; A's later Undo then fails *"changed or was
  replaced"*, indistinguishable from external tampering.
- `begin_transfer` only guards its own window, so two windows can run
  conflicting operations on the same paths simultaneously.
- Closing a window silently discards its entire undo history.

This belongs in the same `OperationCoordinator` move and changes its scope, so
it should be named before that work is estimated.

### M2. The snapshot budget is per-operation, never journal-wide

Review C's P2 "Move history is iterative but still unbounded" is correct —
`move_one` calls `snapshot_tree` with no limit at all
(`src/file_ops.rs:1642`) while Copy uses `COPY_UNDO_SNAPSHOT_LIMIT`
(`src/file_ops.rs:22`, 100 000).

It misses the aggregate. `OPERATION_HISTORY_LIMIT` is 100
(`src/file_ops.rs:21`), and the Copy limit is per operation, so even the
*bounded* path permits on the order of 10⁷ retained `PathSnapshot` values across
a full journal. Giving Move the Copy limit, as Review C recommends, does not fix
that. The budget needs to be journal-wide.

### M3. No startup recovery for interrupted copy and archive staging

`src/app.rs:7312-7338` discovers and reports interrupted `.marcel-delete-*`
quarantine remnants. Nothing does this for `.marcel-copy-*` or
`.marcel-archive-*`. A `SIGKILL` during a copy leaves a `TempDir` staging
directory whose `Drop` never ran, and Marcel never reports or cleans it.

Review C's P3 "hide Marcel-owned staging" covers visibility *during* an
operation. It does not cover remnants *after* a crash, which is the case that
costs disk space silently.

## Upstream evidence

Both upstreams were read at pinned commits before deciding anything.

### Yazi (`319f90e0`)

- **No filesystem undo exists.** The only `undo` in the tree is the text-input
  widget (`yazi-widgets/src/input/actor/undo.rs`). Nothing in `yazi-scheduler`,
  `yazi-fs`, `yazi-core`, or `yazi-actor`. Marcel's journal has no Yazi
  precedent and never did.
- **Move is rename-first with no content inspection**
  (`yazi-scheduler/src/file/file.rs:104`), confirming that a tree Marcel cannot
  copy is still freely movable.
- **`ChaType` enumerates every object kind** — `File/Dir/Link/Block/Char/Sock/
  FIFO/Unknown` (`yazi-fs/src/cha/type.rs`) — rather than collapsing the
  unreproducible ones. Adopted into `SnapshotKind`.

### Nautilus (`f67b2e1`)

- **N1 — undo depth is one.** `NautilusFileUndoManager` holds a single
  `NautilusFileUndoInfo`, and `set_action` clears before storing. No stack.
  Marcel keeps 100 records carrying full tree snapshots.
- **N2 — a failed undo discards the record.** `undo_info_apply_ready` keeps the
  record on success and on user cancellation, and calls
  `file_undo_manager_clear` on any other failure.
- **N3 — user cancellation is distinguished from failure**, and only
  cancellation preserves the record.
- **N4 — no filesystem-identity validation.** No etag, inode, or ctime anywhere
  in `nautilus-file-undo-operations.c`. Undo re-runs the inverse operation
  through the ordinary machinery and lets the interactive conflict dialogs
  absorb whatever changed. The one exception is Trash undo, which matches
  candidates on original path plus deletion time within `TRASH_TIME_EPSILON`
  (`trash_retrieve_files_to_restore_thread`) — an identity check, but a far
  weaker one than device/inode/ctime, and it is refreshed after a successful
  redo (`trash_redo_func_callback`) the way Marcel refreshes snapshots.
- **N8 — Trash undo does not check whether its moves worked.** The
  `g_file_move` call that performs the restore discards its return value
  entirely, and the operation reports success as `restored_at_least_once` —
  true when any entry merely *matched*, regardless of whether it moved. Marcel
  must not copy this; its identity-validating, rollback-on-failure restore is
  stronger than both upstreams.
- **N5 — the action is cleared *before* the async undo runs** (`do_undo_redo`)
  and re-added only on success, so there is no reinsert path at all.
- **N6 — job success means "not cancelled".** `copy_task_done` passes
  `!job_aborted(job)`; per-item problems are resolved by skip/retry/replace
  dialogs mid-operation. Nautilus never produces a partial undo record.
- **N7 — external state invalidates undo.** Emptying the Trash drops a pending
  Trash undo (`trash_state_changed_cb`).

### What this settles

N4 explains why Nautilus never hits D1: it stores no identity that can go
stale. Marcel's strictness is a deliberate divergence — it has no conflict UI to
fall back on, and "no silent overwrite" is a product promise — so Marcel keeps
identity validation and pays for it with D1. N2 and N5 are the cap on that cost,
and they are strictly simpler than the "compensation returns a refreshed record"
approach this document originally proposed, which would have re-introduced R2 by
re-stat'ing objects immediately after a failed operation.

Marcel refines N2 rather than copying it. Nautilus discards on every failure
because it cannot tell a pre-commit refusal from a post-commit one. Marcel's
prepare/commit/finalize discipline can, so a failure that provably never touched
the disk keeps its record and stays retryable.

N1 also reframes M2: Nautilus's aggregate-memory problem does not exist because
depth is one. Marcel need not go that far, but it shows a 100-deep journal of
full tree snapshots is well outside proven practice.

## Plan

Ordered so that each stage closes several findings and does not have to be
redone by a later stage. Stages 1–4 are the hardening gate; stage 5 moves the
code stages 1–4 edit, so it must follow them.

### Stage 1 — Truthful history through compensation — **done**

*Closes D1 and R4. Implemented following Nautilus N2/N5.*

The original plan here — compensation returns a *refreshed* record — was
abandoned after reading Nautilus. Refreshing means re-stat'ing objects
immediately after a failed operation, which is exactly the R2 replacement race,
and Nautilus solves the same problem by discarding instead. Discarding needs no
refresh, so Stage 4 is no longer a prerequisite.

Implemented:

- `MutationOutcome` (`Unchanged` / `Committed` / `Discarded`) replaces
  `Result<CommittedOperation>` for `undo_operation` and `redo_operation`.
  `Discarded` carries the exact `DirectoryChanges` that reached the disk, which
  may be empty after successful compensation — empty still means the record is
  dead, because the compensating rename moved the root's ctime.
- `start_undo`/`start_redo` reinsert only on `Unchanged`. `Discarded` reconciles
  the browser and drops the record with wording naming Marcel's own recovery.
- `remove_snapshotted_tree` reports what it actually removed, so a validation
  refusal stays retryable while a partial erase does not.
- `redone_transfer` derives effects from `CompletedTransfer` plus
  `TransferMode`, which also closes R4 — the mode-blind fallback had been
  marking a copy's source removed.

**Invariant held:** no path reinserts a record whose identities predate a
compensating rename.

**Regressions added:** `a_rolled_back_undo_discards_the_record_it_invalidated`
provokes a genuine post-commit failure using two source parents, one sealed
read-only, since `undo_operation` validates every transfer up front and an
obstacle it can see yields `Unchanged`. `an_undo_that_never_commits_keeps_its_record`
pins the mirror case, including a successful retry after the obstacle clears.

Still open in this area, deferred to Stage 3: `restore_trash_records` and
`retrash_records` currently map any failure to `Discarded`, which is safe but
coarser than their commit boundaries allow.

### Stage 2 — Transfer effects come only from `CompletedTransfer` — **done**

*Closes D2 and R4.*

Delete the record-derived branch in `start_transfer` (`src/app.rs:2349`) and the
mode-blind fallback in `redone_transfer` (`src/file_ops.rs:749`). Both derive
`DirectoryChanges` from `completed` plus `mode`; the operation record becomes
Undo metadata only, never a source of visible effects.

Then decide the partial-Move policy explicitly rather than leaving it emergent.
**Recommendation: all-or-nothing for `0.1.0`.** If any completed move lacks a
record, the whole transfer is non-undoable and no partial `Move` record enters
the journal. It is a one-line policy, it makes `undo_note`'s binary wording
truthful, and it removes a class of surprise that partial Undo would otherwise
require new UI to explain.

**Regression:** move two directories in one operation, one containing a live
Unix socket. Assert both sources disappear, both destinations appear, and Undo
availability matches the notification. Force a Copy redo to lose its record and
assert the source stays visible.

### Stage 3 — An explicit partial outcome, at four sites only — **done** (Sprint 20 closed the quarantine-first remainder)

*Closes A2, D3, R1.*

Introduce the three-state outcome Review C sketches — `Unchanged` /
`Committed` / `Partial` — but apply it **only** to the four paths that cross
more than one commit: `undo_operation`'s `Move` arm, `remove_snapshotted_tree`,
`restore_trash_records`, `retrash_records`. Do not touch single-commit sites;
`CommittedOperation` already models those correctly, and widening the refactor
is how this stage turns into a month.

Within it, make `remove_snapshotted_tree` quarantine-first by reusing
`delete_ops`: atomically quarantine each validated top-level output, then erase.
Make Trash outcomes per-item so a placement that commits without an identifiable
record is reported as committed rather than compensated-away.

**Invariant:** a plain `Err` is legal only where Marcel can prove no committed
effect escaped.

**Regression:** deterministic failure injection on the Nth rename/remove in each
of the four paths; assert the returned state describes disk state exactly.

### Stage 4 — Identity carried across every commit boundary — **done** (Sprint 20)

*Closes R2, R3, and the restore-metadata sub-claim of P1.7.*

`refresh_snapshot_identities` takes the pre-commit `(device, inode, kind)` and
refuses to adopt a mismatch, downgrading to success-without-undo.
`rename_entry` and `reverse_rename` compare against the identity they already
validated. `purge_trash_records` passes an expected `TrashIdentity` into
`delete_trash_backings`, verified at quarantine. The restore path uses the
existing `remove_matching_trash_info` (`src/trash_ops.rs:559`) instead of the
unchecked `let _ = fs::remove_file` (`src/trash_ops.rs:402`).

**Regression:** replace the committed destination between rename and refresh
behind a test hook; replace a payload between purge validation and quarantine.
Assert Marcel never records or deletes the replacement.

Build the failure-injection seam here, not in Stage 8. Stages 1–4 all need it,
and retrofitting it into a hosted pipeline afterwards costs more.

### Stage 5 — Application-global `OperationCoordinator` — **done** (Sprint 19)

*Closes A1, M1, and the bookmark P2.*

One process-global owner of the journal, clipboard, busy state, active jobs,
cancellation, and progress. Windows subscribe through weak references. RAII
cancellation for cancellable jobs; explicit detached ownership for the
non-cancellable commit phase of permanent delete.

Fold the bookmark store into the same pass.
[`review-2026-08-05.md`](review-2026-08-05.md) parked the shared writer as
"later cleanup" on the grounds that the remaining risk was "benign
last-writer-wins" — that judgement is wrong for bookmarks specifically, because
last-writer-wins there is silent user-data loss with no parse error. Browser
view state can keep last-writer-wins.

Must follow stages 1–4: it relocates the code they edit.

**Regression:** start a copy/archive/delete, close the initiating window, assert
the job is either cancelled before commit or still owned and reconciled by the
application. Two windows perform disjoint bookmark additions concurrently; the
final set contains both.

### Stage 6 — Bounded and complete accounting — **partly done** (Sprint 20 bounded every transfer path; the journal-wide budget is still open)

*Closes M2 and the cancellation P2 (and Review C §7.9).*

A journal-wide snapshot budget replaces the per-operation one; Move gets the
same treatment as Copy. Exceeding the budget downgrades to
success-without-undo — moving must stay allowed. Per-source outcomes so that
`completed + failed + cancelled + skipped == requested` for every operation.

### Stage 7 — Physical Trash-root check and honest Trash enumeration — **done** (Sprint 20)

*Closes R5 and the Trash-listing P2.*

Resolve the physical parent (or compare stable directory identity) for
non-symlink delete targets before quarantine, preserving no-follow behaviour for
deleting a symlink object itself. `list_trash_records` returns valid records
plus structured warnings instead of `filter_map(…ok())`
(`src/trash_ops.rs:82`); Empty Trash blocks or announces incomplete enumeration
rather than silently emptying only the subset Marcel parsed.

### Stage 8 — Hosted CI — **open**

*Closes the CI P2. Already Sprint 16 scope; listed for completeness.*

`fmt`, Clippy, tests, Nix build, plus the failure-injection fixtures built in
stage 4. x86_64 Linux mandatory, aarch64 as a release gate.
