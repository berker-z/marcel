# Operation-layer review, 2026-08-05

Recorded: 2026-08-05. Reviewed tree: `482a88a`.

## Context

This document records two independent reviews of Marcel taken on the same
commit, and Marcel's own validation of every claim in them.

- **Review A** was performed in-repository with a build, the full quality gate,
  and executable probes.
- **Review B** was an external AI-assisted source-level review supplied by the
  maintainer. It could not clone or build the repository, so it reasoned from
  source alone.

Unlike [`external-review.md`](external-review.md), this is not design input.
Every finding below was either reproduced with an executable probe or resolved
by reading the exact code path, and each carries an explicit verdict. Findings
marked **Confirmed** are defects in `482a88a`.

Baseline at the time of review: `cargo fmt --check` clean,
`cargo clippy --all-targets --all-features -- -D warnings` clean, 173 tests
passing.

## The governing defect

Review B identified the invariant that ties most of the critical findings
together, and it is the most valuable outcome of either review:

> A function can return `Err` after the filesystem mutation has already
> committed.

Callers read `Err` as "nothing happened". When that is untrue, the disk, the
browser projection, the clipboard, the operation journal, and the user-facing
notification can all disagree at once. Review A did not find this; Review B
did.

The rule Marcel now adopts:

1. **prepare** — all fallible traversal, validation, and journal construction
   happens *before* the mutation.
2. **commit** — one minimal filesystem mutation.
3. **finalize** — infallible in-memory path rebasing.

No mutation API may return an ordinary `Err` after crossing its commit point.
A mutation that commits but whose bookkeeping fails is
**success without undo**, never failure.

## Confirmed critical

### C1. Symlinked destination defeats the copy self-containment guard

*Source: Review B. Verdict: Confirmed, more severe than reported.*

`copy_one` guards self-containment lexically:

```rust
if source.is_dir() && destination.starts_with(source)
```

A symlinked destination is not resolved, so copying `src` into
`alias -> src/sub` is accepted. `staging_path` then places Marcel's staging
directory *inside the source tree*, and because the staging directory is
created before `read_dir(src/sub)` runs, the copy walk enumerates its own
staging directory and descends into it.

Reproduced. The failure message shows the cycle directly:

```
Could not create ".../alias/.marcel-copy-<pid>-0/sub/.marcel-copy-<pid>-0/sub/
.marcel-copy-<pid>-0/sub/..."
```

Review B described termination as "cancellation, path-length failure, or disk
exhaustion". Measured, those are the same outcome, not alternatives: each cycle
appends roughly 26 characters, so `PATH_MAX` permits about 156 cycles, and the
subtree is re-copied on every cycle. With a 1 MiB payload and a sampling
observer:

```
PEAK source payload   = 1048576 bytes
PEAK observed in src  = 163577856 bytes
PEAK amplification    = 156x
```

**156x write amplification, written inside the user's own source directory**
before `cleanup_staging` erases it. A 1 GiB folder writes roughly 156 GiB.

Internal move is unaffected: `renameat2` resolves paths in the kernel and
returns `EINVAL`.

### C2. A committed move is reported as a failure

*Source: Review B. Verdict: Confirmed, deterministic.*

`move_one` renames first, then recursively snapshots the destination with `?`.
`snapshot_from_metadata` bails on anything that is not a directory, file, or
symlink, so **any directory containing a socket or FIFO** reproduces this every
time — not only the "unreadable descendant" Review B proposed. Reproduced with
a Unix socket:

```
MOVECOMMIT reported failures   = 1
MOVECOMMIT reported completed  = []
MOVECOMMIT undo record created = false
MOVECOMMIT source still there  = false      <- the move happened
MOVECOMMIT destination exists  = true       <- the move happened
```

The forward copy path refuses such trees during preparation; `move_one` is a
rename and does not inspect contents until after it has committed.

The browser consequence is worse than lost undo. In `start_transfer`,
`outcome.operation` is `None` and `outcome.completed` is empty, so the fallback
`DirectoryChanges` is empty on both sides and `apply_directory_changes` returns
early. The browser keeps listing a directory that is no longer there, the cut
clipboard keeps a dangling source, and the notification reports failure.

## Confirmed, narrower than reported

### C3. Undo's rollback is skipped on the bookkeeping path

*Source: Review B. Verdict: Confirmed as a defect; reachability overstated.*

In `undo_operation`'s `Move` arm the `if let Err` on the rename rolls back, and
the `snapshot_tree(&transfer.source)?` on the following line does not. That
asymmetry is a genuine oversight.

It is not "the same, worse bug" as C2. `validate_snapshot_tree` runs over every
transfer before any rename, so the tree was provably walkable moments earlier;
only a concurrent change can make the post-rename snapshot fail. A probe that
occupied a source path exercised the pre-flight `ensure_unoccupied` guard
instead and behaved correctly. **Race, not determinism.**

### C4. The same commit boundary is crossed in four more places

*Source: Review B. Verdict: Confirmed at all four sites.*

| Site | Commit | Fallible call after commit |
| --- | --- | --- |
| `copy_one` | `rename_no_replace(staging, destination)` | `rebase_and_refresh_snapshots(..)?` stats every entry |
| `create_zip_operation` | `create_zip_archive(..)?` publishes | `snapshot_tree(&published)?` |
| `extract_archive_operation` | `extract_archive(..)?` publishes | `snapshot_tree(&published)?` |
| `restore_trash_records` | per-item `rename_no_replace` back | `symlink_metadata(original)..?` |

All four require a concurrent change, so P1 rather than P0. The Trash case has
the worst presentation: items are restored to disk, `start_restore_selection`
takes the `Err` branch, and the Trash view keeps listing them.

Review A independently found the same shape in `create_directory_at` and
`rename_entry`, which both `stat` after the mutation.

### C5. Copy staging is not atomically reserved

*Source: Review B. Verdict: Confirmed; the sharp edge is elsewhere.*

The check-then-act on `.marcel-copy-{pid}-{seq}` is less dangerous than
reported, because creation itself is exclusive (`fs::create_dir`, and
`create_new(true)` for files), so losing the race fails safe with `EEXIST`. The
real hazard is the next step: `cleanup_staging` then unconditionally
`remove_dir_all`s whatever occupies that path, **including a file Marcel did
not create**. Requires a local actor who can already write to the destination
directory, so severity is low, but `archive_ops` already models the fix.

### C6. Trash record identification is ambiguous across hardlinks

*Source: Review B. Verdict: Confirmed; very narrow.*

`object_key` is `(dev, ino)`, hardlinks share it, and the candidate search takes
the first identity match. Requires another process concurrently trashing a
hardlink to the same inode; the consequence is a journal bound to the wrong
Trash entry, so Undo restores to the wrong original path. `object_key` also
omits `ctime`, unlike `TrashIdentity`.

### C7. Atomic state writes collide across windows

*Source: Review B, extended by Review A. Verdict: Confirmed, and incomplete.*

`Marcel::new` creates a per-*window* save channel and writer task, every window
in a process shares a PID, and `state::save` uses a non-exclusive
`File::create` on `.state.conf.tmp-{pid}`. Two windows saving concurrently can
interleave writes or rename a half-written file into place. `load` degrades to
defaults, so the impact is silently reset settings.

Review B stopped there. `bookmarks::save` has the identical pattern on
`.bookmarks.tmp-{pid}`, and `start_bookmarks_save`'s re-entrancy guard is
per-entity so it does not help across windows. Corrupt state resets a view
mode; corrupt bookmarks lose user data.

Neither writer syncs the containing directory after the rename, so publication
is atomic but not crash-durable.

## Confirmed by Review A only

### C8. Unbounded recursion aborts the process

`copy_entry`, `measure_entry`, `snapshot_entry`, and `collect_delete_plan`
recurse one stack frame per directory level with no depth cap, on `blocking`
pool threads that use Rust's 2 MiB default stack. Measured with
`transfer_paths(Copy)`:

- dev profile: survives 300 levels, **aborts at 400**
- release profile: survives 1,500 levels, **aborts at 2,000**

The failure is `fatal runtime error: stack overflow` and `SIGABRT`: no
notification, no partial-failure record, mid-mutation, leaving staging behind.
This is inconsistent with `snapshot_paths_cancellable`, `validate_staged_tree`,
`check_staged_limits`, and `validate_compression_sources`, which already use
explicit work stacks.

### C9. Per-frame drag payload is O(directory size)

`selected_file_drag` walks every visible entry, does a `HashSet<PathBuf>`
lookup per entry, and clones each selected path three times. It is called
unconditionally from `render_list` and `render_grid` on **every frame**, not
only when a drag is in progress. Measured on an optimized build against the
50,000-entry directory the sprint documents use as the scale target:

| selection | cost per frame |
| --- | --- |
| one file selected | 1.80 ms |
| all selected (Ctrl+A) | 12.25 ms |

Against a 16.7 ms budget at 60 Hz, before any rendering.

### C10. No path-to-entry index

Every "find the entry for this path" is a linear scan over all entries:
`Render::render`, `command_enabled` (six scans), `activate_primary`,
`begin_rename`, `activate_entry`, `prepare_entry_context_menu`, `end_marquee`.
`render_entry_menu` calls `command_enabled` about fifteen times per frame while
a context menu is open. This compounds C9.

### C11. Lower-tier findings

- Marcel's own `.marcel-copy-*` and `.marcel-archive-*` staging is visible in
  the browser during operations. `show_hidden` defaults to `true` and the
  watcher reducer does not filter Marcel-owned staging names.
- Copy preserves setuid/setgid/sticky bits, unlike `cp`. Verified: a `0o4755`
  source produces a `0o4755` copy. Needs an explicit documented policy.
- `rename_no_replace` has no fallback or specific diagnosis when a filesystem
  does not implement `RENAME_NOREPLACE` (common on FUSE mounts). Every rename,
  move, copy publication, Trash restore, delete quarantine, and archive
  publication fails there with a generic message.
- Cross-filesystem moves are advertised as valid drop targets and refused only
  after the drop; `can_move_files_to` never compares device IDs.
- `system_terminal::spawn` drops `Child` immediately, leaking a zombie per
  "Open in Terminal".
- The freedesktop thumbnail cache directory is created with the ambient umask
  instead of `0700`.
- `IconProvider::discover()` is rebuilt per watcher batch, discarding its cache
  and re-reading `gtk-*/settings.ini`.
- `pdftoppm`, `pdfinfo`, and `gio open` are invoked without a `--` separator.
  Not reachable today because entry paths are always absolute, but
  `archive_ops` already models the correct form.

## Not reachable on `482a88a`

### N1. Basename matching in `retain_uncompleted_move`

*Source: Review B, as P1. Verdict: latent, not a live bug.*

The code reads exactly as Review B describes, but its reproduction requires
`/a/report.pdf` and `/b/report.pdf` in one clipboard, which cannot occur.
`stage_selection` builds the clipboard from `visible_paths()` filtered by
selection, so every clipboard entry shares one parent directory, where
basenames are unique; destinations are `destination.join(name)`, so the mapping
is one-to-one. `start_transfer`'s fallback `removed` computation has the same
shape and the same reprieve.

It remains worth fixing: it becomes a live bug the moment Move To,
cross-directory selection, or queued transfers land. It should not sit above
C1 and C2 in a fix order.

## Assessment

Both reviews agree that `delete_ops.rs` is the strongest module in the
codebase — top-level quarantine before erasure, no-follow traversal, ancestor
identity revalidation, leaf-before-directory removal, and conservative
incomplete-delete reporting. Review A separately confirmed that archive
extraction resists path traversal, symlink and hardlink entries, encrypted
entries, decompression bombs, and argument injection, that the D-Bus surface
validates and bounds its input correctly, and that `xattr` operations do not
follow symlinks.

The operation layer's defect is not carelessness. It is that commit semantics
were implemented independently in copy, move, rename, archive, Trash, and
restore, so each one re-derived the boundary and several got it wrong in the
same way. The fix is one shared outcome type, not six local patches.

## Remediation order

1. Resolve paths before the self-containment check (C1).
2. Move all fallible bookkeeping ahead of the commit, starting with move and
   undo (C2, C3, C4). Introduce one shared committed-operation outcome that can
   express *succeeded but not undoable*.
3. Convert the four recursive walkers to explicit stacks (C8).
4. Replace basename reconciliation with exact transfer records (N1).
5. Reserve copy staging atomically and validate it before cleanup (C5); make
   state and bookmark writes uniquely named, exclusive, and directory-synced
   (C7).
6. Remove the per-frame drag payload and add a path-to-entry index (C9, C10).
7. Work the C6 and C11 backlog.

### What the fixes changed

`CommittedOperation` is now the shared outcome of every mutation API:
`create_directory`, `rename_entry`, the archive entry points, `undo_operation`,
and `redo_operation` all return it, and `TransferOutcome` carries the same
distinction through `undo_unavailable`. It pairs the always-known published
path and directory-reducer effect with an `Option<OperationRecord>`, so a
mutation whose bookkeeping failed reports success without undo and the browser
projection still reconciles against the disk.

Two things surfaced during implementation that neither review predicted:

- **A same-filesystem rename bumps the renamed inode's `ctime`** while leaving
  every descendant untouched (verified directly). Review B's premise that
  "device, inode and ctime survive a same-filesystem rename" is wrong for the
  root, so simply moving the snapshot ahead of the rename would have silently
  broken undo for every move. The move path now snapshots before the commit,
  rebases infallibly, and re-reads identities afterwards, downgrading to
  success-without-undo if that fails.
- **Snapshotting must not be a preconditon of moving.** Making
  `snapshot_tree` fallible before the rename first turned any directory
  containing a socket from a misreported success into an outright refusal — a
  regression caught by the new test. A rename does not care what a directory
  holds, so the pre-walk is best-effort bookkeeping: unsnapshottable trees
  still move, they just cannot be reversed.

C7 keeps one writer per window; the collision and corruption risk is removed by
reserving each temporary file atomically and syncing the parent directory after
publication, leaving only benign last-writer-wins. A single process-level
coalescing writer remains available as later cleanup.

Regression coverage added: resolved self-containment for copy and move, a
committed move over an unsupported child, deep-tree copy and delete on a
2 MiB worker stack, exact-path clipboard reconciliation, entry-index
invalidation across every `entries` mutation, and selection-revision coverage
of every mutator. The suite is 181 tests, with `cargo fmt --check` and
`cargo clippy --all-targets --all-features -- -D warnings` clean.
