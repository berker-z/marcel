## D1 — Directory merge violates the commit boundary. **Confirmed, P0.**

`merge_directories` (`src/file_ops.rs:2520`) returns
`Result<Vec<PathSnapshot>>` and uses bare `?` at three sites after mutation has
begun:

- `:2534`, `fs::create_dir` for each planned directory;
- `:2545`, `copy_one` for each planned file;
- `:2555`, the deferred `symlink_metadata` that snapshots the created
  directories.

The caller folds that `Err` into `failures` (`src/file_ops.rs:1670`) and extends
`merged_created` only on `Ok` (`:1664`). So directories created and files
published before the failure are real on disk, absent from `merged_created`,
absent from the `Copy` record assembled at `:1782`, and therefore unreachable
from Undo.

This is the precise shape `CommittedOperation` was introduced to make
unrepresentable: *the filesystem changed, the function returned failure, and the
caller concluded no committed effect escaped.* The function's own comment
(`:2543`) states the weaker invariant it does hold — no individual file is ever
reachable half-written — which is true and is not the invariant at issue.

Review D's suggested shape is right. The fix is an outcome type carrying the
additions on the failing path as well as the succeeding one.

## D2 — A failed rollback leaves recoverable data in sweepable storage. **Confirmed, P0.**

Three code paths put a user's original into `.marcel-replaced-*` storage and
then lose the handle to it:

1. **Forward transfer.** A transfer that fails after its destination was
   quarantined calls `restore_replaced_items` (`src/file_ops.rs:1766`). If that
   fails, the message names the quarantine path (`:1768-1771`) and the
   `ReplacedItem` is dropped. It never reaches `replaced_items`, so it never
   reaches the `Copy`/`Move` record at `:1787`/`:1793`.
2. **Undo of a copy.** `:881` returns `Discarded` when restoration fails after
   the copy output was removed.
3. **Undo of a move.** `:968` does the same after every rename was reversed.

In all three the quarantine is reachable only from a message the user may
already have dismissed. `release_unreachable_quarantines`
(`src/operations.rs:214`) drains the *journal*, so the application owner does
not protect it either.

The composition Review D describes then completes:
`reclaim_abandoned_quarantines` (`src/file_ops.rs:2694`) treats any
`.marcel-replaced-*` whose owner process is gone as provably unreachable garbage
and erases it.

**Reachability is higher than Review D states.** The sweep is not a startup
scan. It is spawned on every completed directory listing
(`src/app.rs:796-801`). The sequence is therefore:

> failed replacement → failed restoration → restart Marcel → *browse that
> folder* → the original is deleted.

The comment justifying the sweep (`:2690-2693`) is sound for its intended
subject — an original the user chose to overwrite, whose replacement succeeded —
and unsound for this one, where the replacement did *not* succeed and the
original is the only copy. One name is being asked to mean two things.

Review D's prescription is adopted verbatim in Sprint 20: undo storage stays
sweepable, and a failed restoration promotes its quarantine into recovery
storage that is never swept and is surfaced to the user.

**Prior art in this repository.** `.marcel-delete-*` remnants already work this
way: `quarantine_recovery_warning` (`src/app.rs:6731`) surfaces them in the
browser, and `is_internal_working_name` (`src/file_ops.rs:2655`) deliberately
does *not* hide them so the guidance can point at the path. Recovery storage
should join that convention rather than invent a second one.

**This was a known blind spot.** Sprint 18's last unchecked acceptance box reads
*"deterministic failure-injection coverage for a failure arriving after a
replacement has been quarantined but before the replacement is published."* The
path shipped untested, and the defect is in it.

## D3 — Quarantine deletion trusts the path, not the identity. **Confirmed, P1.**

`erase_replacement_quarantine` (`src/file_ops.rs:2800`) takes a bare `&Path`,
stats whatever is there, and `remove_dir_all`s it if it is a directory. Its
justification (`:2801-2802`) — that Marcel created the path by atomic rename
under a process-namespaced name, so nothing else can hold it — is true at
creation and not at eviction, which can be arbitrarily later.

`ReplacedItem` already carries the `FileIdentity` (`src/file_ops.rs:211-224`)
that would settle it. Every caller has the item; only the function signature
throws it away.

Callers: journal eviction (`:606-610`), the over-budget release (`:1749`), the
never-recorded release (`:1799`), coordinator shutdown
(`src/operations.rs:231`), and `reclaim_abandoned_quarantines` (`:2707`) — the
last being the only one with no identity available, and the one Review D
correctly says should simply err conservative.

## D4 — Merge defeats the undo snapshot budget. **Confirmed, P2.**

Ordinary copy threads the remaining budget across sources
(`src/file_ops.rs:1705-1717`), halving it per source so a single source cannot
consume the operation's whole allowance. Merge passes the full
`COPY_UNDO_SNAPSHOT_LIMIT` constant to `copy_one` for every leaf
(`:2545`) and accumulates the results into one vector (`:2546`).

The bound is therefore per leaf, not per operation, and the record for a wide
union is unbounded in the way the constant's own documentation (`:27-39`) says
it must not be. No corruption; the resource-control model simply stops being
enforced where it is easiest to exceed.

## D5 — Cancelling a merge is reported as failure. **Confirmed, P1. Review D missed this.**

Same function, same root cause, distinct user-visible defect.

`merge_directories` signals cancellation by `bail!("Operation cancelled")`
(`src/file_ops.rs:2531`, `:2540`), which is indistinguishable at the call site
from a genuine error. `transfer_paths_impl` therefore pushes the cancelled
source into `failures` (`:1670`) rather than into `cancelled_sources`, and does
not break the loop — so a user who cancels a merge is told the merge *failed*,
while the remaining sources are still attempted until the loop's own
cancellation check (`:1628`) catches up.

This contradicts two written contracts:

- Sprint 18's acceptance check *"cancelling from a conflict stops the operation
  and is reported as cancellation, not as failure"* — which is unchecked, and
  now known to be false rather than merely unverified.
- `TransferOutcome`'s stated purpose (`:389`), that cancellation is accounted
  separately from failure precisely so a cancelled operation does not read as a
  broken one.

The partial additions are lost as well, for the D1 reason. One outcome type
fixes both.

## The smaller notes

**`NAME_MAX`. Confirmed, P2.** `quarantine_for_replacement` builds
`.marcel-replaced-{pid}-{sequence}-` and appends the original name
(`src/file_ops.rs:2730-2733`) with no length bound. The prefix costs roughly 25
bytes, so replacing a file whose name exceeds about 230 bytes fails at the
rename with `ENAMETOOLONG` — a refusal caused entirely by Marcel's own
bookkeeping. `reserve_quarantine_path` in `delete_ops` (`src/delete_ops.rs:357`)
has the identical defect and should be fixed with it.

**`OperationCoordinator` size. Agreed, no action.** 1,533 lines including tests,
holding orchestration and the GPUI conflict dialog. Review D's advice — that it
is still cohesive, that the conflict presentation is the part that will
eventually move, and that it must not be dissolved into generic traits or an
event framework — matches what
[Sprint 19](sprints/019-application-global-operations.md) already decided and
what `TODO.md` already records. Nothing to schedule.

**Sprint 19 acceptance. Agreed.** Its eight multi-window checks are unrun and
unreachable by `cargo test`; the sprint document says so itself. They are
carried into Sprint 20 unchanged.

## What Review D confirms, correctly, as fixed

Recorded so a future review does not re-derive it:

- Copy publication stages privately and publishes with a no-replace rename.
- Self-containment resolves real paths, closing the symlink recursion defect.
- Move snapshots are bookkeeping, not a precondition for the rename.
- Visible changes come from `CompletedTransfer`, not from inferred undo records
  (Stage 2 of [`review-2026-08-10.md`](review-2026-08-10.md)).
- The no-interface conflict path refuses visibly: although `ConflictPolicy`'s
  noninteractive default is `Skip`, `plan_source` converts a noninteractive
  occupied destination into a reported refusal before that default is consulted
  (`src/file_ops.rs:1514-1518`).
- Apply-to-all state is independent per response kind, and alternative naming
  handles non-UTF-8 names without producing `foo (2) (2).txt`.
- The blocking conflict resolver waits on the blocking pool, and a lost receiver
  yields cancellation rather than a parked worker.
